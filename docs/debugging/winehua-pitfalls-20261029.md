# WineHua 适配踩坑记录：桌面、启动、输入与构建

整理日期：2026-10-30，验证记录截至 2026-10-29。本文记录实际遇到的问题、排除过的错误判断及当前处理边界。
对应的 [IME 专项 PR](../pr/ime-key-scancode.md) 仅提交扫描码修复、构建接线和相关测试。
其余章节保留为本轮适配复盘及后续拆分依据，不表示这些改动已包含在本 PR。
没有记录的硬件/游戏组合不由此推断兼容；旧候选的结论不能自动套用到新载荷。

## 一、虚拟按键：每一层“收到”都不等于游戏能用

### 1. 最关键的坑：VK 正确，SDL 仍可能认不出按键

**现象**：数字 1～5 和 Esc 的宿主日志都有按下/抬起；普通窗口能收到数字 VK，
但真实《暗黑地牢》忽略按键。Esc 从约 100 ms 延长至约 1500 ms 仍不响应。

**根因**：`ImmTranslateMessage()` 传给 `ImeToAsciiEx()` 的 `vsc` 是原始消息
`lParam` 的高 16 位。IME 回退直接 `.lParam = vsc`，转发后扫描码不在 bits 16–23，
扩展键、重复及释放标志也不在原位置。VK 值本身正确掩盖了这个错误。

**修复**：用 `MAKELPARAM(1, vsc)` 重建参数；未消费输入时正确区分
`WM_IME_KEYDOWN` 与 `WM_IME_KEYUP`。不关闭输入法，也不改变游戏键位。

**如何防复发**：验证 evdev → Wayland → Wine 消息 → 真实游戏四层；消息检查必须覆盖
`wParam`、`lParam` 的扫描码及状态位。当前专项从实际初始化语句生成可执行回归，
覆盖 10 种键 × 3 种状态 × 2 条路径，共 60 项；旧代码失败，修复后通过。
这 60 项不是 60 次游戏人工验收。

### 2. 另有时序问题，但它不能解释所有无响应

| 踩坑 | 已采用的处理 | 必须保留的边界 |
| --- | --- | --- |
| 快速触摸在游戏一次轮询内完成按下/抬起 | 虚拟单键最短保持 100 ms | 不改物理键盘、摇杆的正常时序；长按释放不再补时 |
| 定时释放晚于控件销毁或新一次点按 | 取消待执行计时器，重新点按前清理旧所有权 | 隐藏、移除、切换编辑、离开页面均要检查 |
| 另一根手指抬起导致当前按键释放 | 以触点 ID 判断实际所有者 | Cancel 与真正拥有者 Up 分别覆盖 |
| 多个控件共享同一按键，松开一个就全部松开 | 目标/键码维度引用计数 | 最后一个持有者释放后才发送 key-up |
| 只测单次点按，不测长按和连按 | 执行实际 TouchControlView 方法测试 | 不用重写一份假控件逻辑代替真实方法 |

### 3. 焦点和 modal 是另一条独立故障链

桌面 root 的键盘焦点不等于游戏窗口焦点；鼠标悬停位置也不应替代已经建立的有效键盘焦点。
游戏 owner 被 modal 禁用后，仍给 owner 发键看似成功，却不能关闭弹窗。
弹窗销毁后还要恢复有效目标，并处理释放事件，不能把“关闭 modal”当作输入已经完全恢复。

当前策略保留有效子窗口焦点，失效/桌面焦点回退到可见应用，显式可见 modal 优先。
受控来宾 fixture 已记录：虚拟 Enter 关闭 modal、中/右键成对到达、关闭后数字键继续到达。
受控 fixture 与真实游戏自己的错误弹窗必须分别验收。

### 4. 鼠标按钮不是键盘键码

`BTN_LEFT`、`BTN_MIDDLE`、`BTN_RIGHT` 应走 pointer button 通道；不能为了复用 UI
把它们塞进 `sendKeyEvent()`。按下捕获目标，抬起配对；光标覆盖层不参与命中测试，
点击虚拟键时也不能顺带把游戏光标移动到虚拟键的位置。

## 二、黑屏：先区分没有内容、无法合成与无法呈现

| 现场证据 | 容易误判为 | 实际处理 / 结论 |
| --- | --- | --- |
| EGL 初始化成功，但 root 长时间 0×0 | GPU 初始化失败 | 追踪 root 识别、configure、attach/commit；成功创建 EGL 不能证明来宾已有内容 |
| root 没有 pixels，子窗口已有真实 buffer | 所有客户端都没画面 | 合成器允许在自身基底上合成已有子内容；不伪造 guest root 状态 |
| 固定分辨率关闭物理 resize 反馈后没有首帧 | 调整更多缩放参数 | 提供独立的会话 logical output 首 configure 来源，在锁外发送 |
| 重新进前台但尺寸没变 | 不需要重绘 | 新 Surface 和前台恢复即使同尺寸，也可能需要重画缓存 |
| 新帧已被消费但 swap 失败，随后静态跳帧 | 没有新 commit 就没有工作 | 成功 swap 才确认请求；失败保留重试，旧 swap 不能清掉更新的请求 |
| 旧 XComponent 的 destroy/resize 迟到 | 当前窗口被销毁或缩放 | 携带并核对 surface 身份，忽略旧事件；替换前停止并 join 旧 renderer |
| 缺 producer buffer、随后出现 GL 错误 | 每帧销毁整个图形栈 | 16 ms 有界等待、250 ms 恢复限速，只重建失败的 producer surface |
| 临时 framebuffer 探针读到黑色 | 最后合成透明度一定有问题 | 此现场说明至少不能只怪最终合成；还需追踪上游内容和呈现路由 |

首 configure、renderer 恢复和无 buffer root 合成解决的是不同条件，需要组合验证。
普通 VirGL 下仍黑时，SurfaceQueue 错误不再出现也不能写成游戏已经修好。
当前暗黑地牢的可见画面依赖已验证的受管 Zink 路径；不泛化到所有设备或游戏。

临时像素扫描、逐帧日志必须撤掉或受诊断开关控制；HAP 应确认不含临时 `PIXEL-PROBE`。
`state:ready`、有客户端 FPS、成功读回或成功上传均不足以单独证明最终画面可见且方向正确。

## 三、启动路径：同一 EXE 也可能得到不同环境

### 1. 字体兼容误带 CSMT 设置

旧兼容分支为端午版同时设置单色字形与 `WINE_D3D_CONFIG=csmt=0`。
Unix 启动器传给真正游戏子进程的环境含这项覆盖，Wine Explorer 创建的 Windows 子进程
环境却没有；两条启动路径因而使用不同的 WineD3D 命令流线程策略。

处理是解耦这两个开关，默认保留字形兼容、移除强制 CSMT 覆盖。显式用户配置仍优先；
同步 GDI 仅作明确开启的诊断回退。提高 Box64 档位不是这个问题的根因修复。

### 2. 文件名和路径近似不等于程序相同

- `C:\games` 与下载目录映射的 `Z:\games` 在实测设备上是不同目录，需比较卷/文件身份。
- 游戏目录可能同时含 `_windows`、`_windowsnosteam`、32/64 位和多个辅助 EXE。
- 自动入口应排除安装、卸载、工坊上传、翻译与存档迁移工具，同时保留手动选择。
- 验收暗黑地牢明确使用 `/_windows/win64/Darkest.exe`；不能拿另一个入口的成功替代。
- 目录、参数、环境与 CPU 预设应共用启动契约，并记录真正子进程的最终生效值。

### 3. 后台 Ability context 导致前台失败

从后台 EntryAbility context 请求桌面会被系统以 201 拒绝。若只等“窗口就绪”超时，
会把平台拒绝误报成 Wine/图形启动失败。产品游戏库应使用当前前台 Ability context，
再复用既有平台就绪策略；“请求成功”和“实际有画面”继续分别确认。

## 四、图形和性能：保留有效策略，记录撤回实验

| 项目 | 当前处理 | 不能据此声称 |
| --- | --- | --- |
| 专用 Zink 档 | 已验证设备/资源/程序限定；用户明确环境优先 | 所有游戏默认强制 Zink 均兼容 |
| Mewgenics 磁盘 dynacache 崩溃 | 按程序关闭磁盘缓存，保留运行期 dynarec，不删除缓存 | 已修复 Box64 上游所有映射/缓存崩溃 |
| Zink staging 复用与 BO cache 预算 | 保留容量、引用、完成状态等限制和原有同步 | 删除 fence/barrier 也安全，或整场功耗下降某个比例 |
| Venus 带回复提交通知 | 发布命令后通知，异步绘制仍沿用通知合并 | 它是异步读回或 GPU 零拷贝 |
| Wine direct SHM | 保留显式实验开关、所有权与原路径回退；默认关闭 | GPU→CPU readback 已被消除 |
| 局部纹理上传 | 目标场景无明确收益，实验已撤回 | 单个矩形少传输等于整场游戏提速 |
| 独立读回合并提交、每帧 PBO、错误 glthread 组合 | 不进入最终配置 | 编译成功或局部单测通过就该保留 |

Mewgenics 同一家园参考采样仍在约 9 FPS 基准附近，没有证明显著提高帧率或降低功耗。
端午版的 Explorer/游戏库相同轨迹短时显示 FPS 中位为 65.484 / 64.524，支持启动表现接近，
不是受控条件下的精确收益百分比。

测量时区分客户端 commit 和实际显示，样本按更新序号去重。角色位置、提示框状态、
分辨率、画质、payload、温度和频率条件不同时不能直接比较；CPU PMU 不是 GPU 或总 DDR。
一次 1200 帧四象限正确性验证也不等于真实游戏长跑或性能验收。

## 五、构建与安装：最容易出现“修好了但包里还是旧代码”

### 1. Wine 补丁必须进入构建链和最终载荷

只改第三方源码、只重建 `libentry.so` 或只打 HAP，都不保证 `wine-data.zip` 中的来宾
DLL 已更新。应核对补丁应用、两架构编译、ZIP 成员、payload manifest、包内容与设备文件。

GNU patch 的反向探测还有一个陷阱：`--reverse --dry-run --batch` 可能检测到未反向补丁后
自动忽略 `--reverse`，退出码却为成功，造成“补丁已应用”的误判。反向探测使用
`--force` 固定方向，随后正向应用；应保留原代码失败与修复后通过的同一回归证据。

### 2. 仓库目录看似 submodule，不代表独立 Git 元数据可用

检查 `git -C <目录> rev-parse --show-toplevel` 的实际结果和父仓库的 submodule 记录。
当前 Windows 源副本中，对 Wine 目录执行 Git 命令曾回落到父仓库，使针对 Wine 内部
相对路径的 diff 为空；不能据此认定源码未改变。修复通过非空、可重放的补丁及构建接线保留。
若改用 fork 提交，需保证子仓库提交已推送、主仓库指针可获取，不提交指向私有/未推送对象的指针。

### 3. 运行时 hash 改变，不能顺手重置用户数据

当前界面“应用引擎更新（重置）”会调用完整 reset，可能清理 prefix。覆盖安装 HAP
和重置 Wine 环境不是同一个操作，不能因 manifest 不一致自动清数据。

v17 的已知迁移：旧 manifest 匹配原载荷，候选包逐项确认仅 x64/x86 `imm32.dll` 改变，
先备份、更新并回读核对运行时/prefix 的四份 DLL，再同步对应新 manifest，重启后引擎 ready。
这是特定版本的验证操作，不是通用无损升级实现；未知载荷不能只改 hash 冒充已升级。

打包指定候选运行时时，应先备份工作区 rawfile，构建后在 `finally` 恢复并复核哈希。
输出文件名或修改时间不能证明安装的是哪个版本。CRC/内容校验也不替代签名证书链校验。

### 4. 测试工具自身也会制造假失败和假通过

| 踩坑 | 处理 |
| --- | --- |
| HDC 使用相对源路径，传成包含目录的同名文件夹，Wine 实际打开 Explorer | 传绝对源文件路径和明确目标目录；回传比对 SHA-256，确认执行的是 EXE |
| 用旧报告的 `failures=0` 作为新长跑成功 | 唯一运行目录、检查本次起止标记、实际帧数与最终图像 |
| 使用过期截图坐标，点击落到桌面或其他应用 | 每次重新获取布局，校验 WineHua/桌面标识，再解析控件位置 |
| 本机 `snapshot_display` 拒绝 `.png` | 使用工具实际支持的 `.jpeg` 后缀，检查生成及传回结果 |
| PowerShell 读取无 BOM UTF-8 脚本，非 ASCII 虚拟机路径乱码 | 明确 UTF-8 解码或为 Windows PowerShell 使用相应编码；凭据不打印进日志 |
| 虚拟机未启动或重启后共享目录未挂载 | 先确认 VM/挂载状态；可用 guest 临时目录编译并取回，不能把路径错误当作源码失败 |
| Unicode Win32 API 配合窄字符资源宏，严格编译失败 | 明确 `UNICODE` / `_UNICODE`，保留警告为错误，不靠关闭诊断通过 |
| 多个诊断进程同时写同一个日志 | 使用每次运行/每种探针独立输出，避免旧进程覆盖或混入新证据 |

## 六、仍然要分清的验收边界

- **已实测**：真实游戏 Esc 菜单响应、v17 覆盖安装、四份 DLL 哈希及运行时 manifest、安装后引擎 ready。
- **专项/受控验证**：60 项 IME 消息字段、虚拟控件时序与所有权、受控 modal 及中/右键配对。
- **历史独立验收**：桌面固定/自动与恢复、无 buffer root、1200 帧 GL 最终四象限；不是在 v17 上全部重跑。
- **仍待补充**：1～5 每项独立图像验收、真实错误弹窗、多设备、长跑、中文组合输入、干净环境完整构建及项目要求的全套设备门禁。
- **未建立归因**：个别回桌面/SIGKILL 现场，不能都归因于同一个渲染或应用崩溃问题。

提交时附当前结论和必要证据，不把已撤回实验复活，不把诊断规避写成上游根治。
公开材料不包含设备序列号、账号、绝对个人路径、完整日志中的环境变量、凭据、证书或存档。
